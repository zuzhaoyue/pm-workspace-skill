> 本项目沉淀 悦动健身会员系统 的业务知识与协作规范。Claude 每次工作前必读本文件,
> 并按下方索引读取相关业务上下文。

## 项目背景

- 我是 悦动健身会员系统 的产品经理。这是连锁健身房的会员与课程管理系统,
  门店店员和会员都要用;靠会员卡(月/季/年)与私教课时包收费。
- 产品全貌、端划分、全局约定见 `业务上下文/00-产品概览.md`(**做任何需求前先读它**)。
- **业务上下文按上线状态分三个文件夹**:`已上线业务/`(线上现状)、`已确认需求/`(定了没上线)、
  `沟通中需求/`(还没定)。**读之前先看它在哪个文件夹** —— 拿 `沟通中需求/` 里的东西
  去答客户或排开发,是本项目最容易犯的错。

## 协作方式

1. **需求信息不全时,一问一答向我确认**,一次只问一个问题,不要一次抛一堆。
2. **不得基于猜测撰写**。未确认的细节标 **【待确认】**,并配「谁在什么时间做了什么」的
   通俗事例,同步进对应功能的待确认清单。
3. 我偏好**简单、一致、少例外**的规则设计;方案对比要讲清取舍。
4. 业务规则文件是**权威口径**,与旧文档冲突时以业务规则文件为准;
   不得默默推翻已锁定规则,冲突时先提醒我。

## 知识维护规则

- **未上线的新需求不要和线上现状混写**:业务规则文件顶部必须写上线状态;
  文件内描述线上现行行为的地方标 **【已有功能】/【线上现状】**,其余默认是待开发规格。
- **业务规则有更新** → 改 `业务上下文/<对应文件夹>/` 下的文件,**再回头同步 PRD**
  (硬性要求。改完知识库没改 PRD,下次就会按旧口径写)。
- **待确认被拍板** → 从待确认清单移入业务规则文件,并同步 PRD 正文与附录。
- **功能上线状态变了** → **整套文件换文件夹**(沟通中 → 已确认 → 已上线),
  并同步 `00-产品概览.md` 的功能索引和本文件「当前状态」。文件夹是唯一的状态标识,
  别只改文字不挪文件。
- **新增功能** → 新建 `<功能名>-业务规则.md / -术语表.md`,视情况配 `-待确认清单.md`
  和 `-决策记录.md`,并在 `00-产品概览.md` 功能索引登记。
- **重要决策被推翻 / 敲定过程曲折** → 记入该功能的决策记录,避免日后重提已否决方案。
- **待确认编号 = 组字母 + 组内序号**(A1);删除时同组后面的不重新编号,只标为已关闭。
- **文档语言**:内部文档与产品 UI 均为中文,不需要文案对照表。
