# PRD 写作规范

> 这是一份**通用骨架**,不是哪家公司的定稿规范。你们团队有自己的约定,
> 直接改这个文件 —— 它就在你的工作区里,改了只影响你自己的项目。

## 0. 四条总原则(动笔前先过一遍)

1. **PRD 是给开发和测试看的。** 一句话如果回答不了「开发要写什么代码 / 界面要显示什么」,
   就删掉,或压成一句带指针。
2. **只写本次要做的东西。** 线上已有、本次不改的行为不写。
   判断办法:**这段删掉,开发会不会做错?不会 → 删。**
3. **只写当前结论,不写沿革。** 不出现「原 X 已作废」「由 X 改为 Y」「改过几版」。
   要追溯去看决策记录文件。
4. **页面章写清楚了,规则章不要再叮嘱一遍。** 「必须提醒用户 X」这类句子没有实现内容 ——
   页面章已经写了「按钮上方显示提示行,文案见下表」,规则章再写一条「必须告知」是写给谁看的?删。

⚠️ 第 2、3 条有个重要例外,**作为规格的否定句要留**:
「订单状态不新增取值」「这个页面不给日期选择器」「该段不单独拆行」——
**这些不写清,开发很可能就按相反的做了。**
删的只是「线上现在长这样、本次不改」这类陈述,和「不是 X」这类纠正话术。

## 1. 章节结构

```
# <功能名> PRD
   阅读说明(一句话:正文只写本次要做的东西)
# 1 原型图
# 2 共用规则        ← 只放两类东西,见 1.1
# 3 <端 A>          ← 按端分章,如「客户端」「管理后台」
# 4 <端 B>
# 5 通知与邮件汇总
# 6 附:待确认事项
```

单端功能省掉端的分章,直接按页面排。

### 1.1 「共用规则」章只放这两类

- **多个端都要用、正文反复引用的口径**(计费、生效时间、状态流转、速查表)
- **展开太长、塞进流程会打断阅读的**(复杂算法与算例)

**只在一个页面用到的规则,搬进那个页面的章节、原地写。** 常见的误放:

| 内容 | 该搬去哪 | 为什么 |
|---|---|---|
| 某按钮在什么条件下置灰 | 那个页面的「入口与按钮状态」 | 本质是按钮状态,写在入口处才读得懂 |
| 风险提示的文案 | 那个按钮所在的小节 | 它是界面文案,不是规则 |
| 只发一次的某封通知 | 整节删,字段并进「通知汇总」章 | 汇总章就是干这个的 |

搬完以后,正文走到哪一步要用哪条共用规则,**就在那一步原地写「见共用规则『XXX』」** ——
别让读者自己去翻。

## 2. 页面小节一律三段式

描述页面的小节,都按这个骨架:

```
**【显示说明】**  页面上有什么、字段取什么值、什么条件下显示
**【交互说明】**  1. 点什么 → 2. 系统做什么 → 3. 另一个分支
**【特殊场景】**  例外、边界、拦截、失败、与别处的约束
```

- **【交互说明】只列 1/2/3 短句**,一句一步,不展开论证。
  「为什么这样设计」「超上限怎么弹框」全部挪进【特殊场景】。
- **没内容的块直接省略**,不要写空标题。
- 通知 / 邮件类小节不是页面,不套这个骨架。

### 2.1 句式:一律「词语:解释」

每条先给**字段名 / 按钮名 / 条件名**,冒号后写它是什么、取什么值、怎么算。

- ✅ `**按钮显示条件**:当前账号的套餐状态为【生效中】。`
- ✅ `**生效时间**:只读文案「即时生效」,固定为当天,客户端不给日期选择器。`
- ❌ `页面上会显示一个只读的生效时间,因为客户端不开放选择,所以……`

## 3. 待确认项写法(最容易写废的一节)

- **编号 = 组字母 + 组内序号**(A1 = A 组第 1 条)。清单、PRD 附录、正文引用**一律用这个编号**。
- **状态标记只有两种**:
  - **【暂定口径已写入正文 · 待确认】** —— 有暂定逻辑,开发照正文先做
  - **【⚠ 无暂定口径 · 开发前必须先定】** —— 正文空缺,不定没法实现

  不要用「仍未定 / 已暂定」这种**容易被读成「有的已经定了」**的说法。
  待确认里的条目**都是未定的**。
- **每条必须配一个通俗事例**:「谁、在什么时间、做了什么、然后期望看到什么」。
  涉及金额的给**具体数字对比**(「先截后乘 = 14,490,先乘后截 = 14,505,差 15 元」)。
  > 反例:「金额为负时怎么处理」—— 两周后没人记得这在说哪个场景。
- 备选分支**各自独立成子项缩进**,不要挤在一句话里用「vs」带过。
- 每条末尾写「若被推翻要回改」,列出连带要改的小节。
- **新增加在该组末尾;删除时同组后面的不重新编号**,只标注为已关闭 ——
  历史文档里引用过的编号一旦错位,追溯就废了。
- **PRD 附录与 `<功能>-待确认清单.md` 逐条对齐**:编号、标题、事例、备选、倾向都一致。
  只有引用写法不同 —— **PRD 一律用「小节名称」引用、不写章节号**
  (PRD 会被复制进别的文档,章节号对不上要一个个删)。
- 增删待确认时,**同步各处的条数**:PRD 附录、清单顶部的索引表、`00-产品概览.md`、`CLAUDE.md`。

## 4. 涉及计算的内容(计费、配额、折算等)

- **先给总公式 → 再给分段公式 → 最后给逐步算例**。
- 算例写明每段的**期间 + 天数 + 算式**,不要只给最终数字。
- ⚠ **取整口径必须写死**:是「先乘后截」还是「先截后乘」,每一步截还是最后截。
  不写死,开发和财务算出来的数就会差几块钱,而且谁也说不清谁对。
- **边界口径要和所有出现它的地方对齐**(账单明细、订单详情、算法说明三处必须一致)。

## 5. 通知与邮件汇总

### 5.1 编号

- 给客户的和给内部的**分两套前缀**(如 `MC#` / `MB#`),一眼能分辨收件对象。
- 编号在整个需求里通排,单份文档用到其中几个、中间断号很正常,**不要为了连号重排**。
- ⚠ 通知编号和待确认编号**不是一套东西**,章首要写明,否则「见 C1」无从分辨。

### 5.2 表结构:不要「状态」列

表头固定 **# ｜ 场景 ｜ 触发时点 ｜ 收件人 ｜ Cc ｜ 内容要点**。

「状态」列会变成垃圾抽屉,装三样东西,各有各的归宿:

| 装的是什么 | 例子 | 处理 |
|---|---|---|
| 口径定没定 | 「已定」「不改」 | **删** —— 没定的才需要标 |
| 沿革 | 「时点由 3 天改为 7 天」 | **删** |
| 真规格 | 「升级本身不发」「与 MC3 互不替代」 | **归位**到触发时点 / 内容要点 |

真·待定改标 **【待确认】**,放进对应那一列。

## 6. 列表页与详情页的分工

反复出现的信息架构问题,定一次就别再犯:

- **列表 = 轨迹**,每行给「这次操作之后的状态」;**详情 = 单笔凭证**,给构成、金额、前后对比。
- **变更前后的对比只放详情,列表不加列** —— 加了列表就宽得没法看。
- 非变更类的事件(新购、续费)也纳入同一张列表,变更专属列显示「—」。

## 7. 改完之后

1. **业务规则改了 → 必须回头改 PRD**(硬性要求)。改完知识库没改 PRD,下次就按旧口径写了。
2. **待确认被拍板 → 从清单移进业务规则文件,并从 PRD 附录删掉那条。**
3. 要追溯「为什么这么定、否决过什么」→ 写进 `<功能>-决策记录.md`,**不要写进 PRD 正文**。
